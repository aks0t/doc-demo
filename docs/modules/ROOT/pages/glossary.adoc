= Глоссарий терминов

Термины, используемые в документации CRM Leads API и связанных бизнес-процессах.

[cols="1,3"]
|===
| Термин | Определение

| Lead (лид)
| Потенциальный клиент, оставивший контактные данные через веб-форму, звонок,
партнёра или добавленный вручную. Основной ресурс API (`/leads`).

| Deal (сделка)
| Коммерческое предложение, сформированное отделом продаж после квалификации
лида. В текущей версии API не выделена в отдельный ресурс — фиксируется
статусом лида (`qualified` → `closed`).

| XRM
| Обобщающее название для CRM-подобных систем (Customer/Any Relationship
Management) — управление отношениями с любыми контрагентами, не только
клиентами.

| Квалификация лида
| Проверка лида на соответствие критериям (бюджет, потребность, наличие
права принятия решения — ЛПР) перед передачей в отдел продаж. Выполняется
маркетингом.

| ЛПР
| Лицо, принимающее решение — контакт на стороне лида, уполномоченный
согласовать сделку.

| SLA
| Service Level Agreement — согласованный срок реакции на событие. Например,
SLA на квалификацию лида — 4 рабочих часа.

| Access Token
| Токен доступа, выдаваемый через `POST /auth/token` по схеме OAuth 2.0
Client Credentials. Живёт 3600 секунд, не обновляется через refresh-токен.

| Идемпотентность
| Свойство операции, при котором повторный одинаковый запрос не создаёт
побочных эффектов сверх первого вызова. У `POST /leads` этого свойства нет:
повторный запрос с тем же `email` вернёт `409 duplicate_email`.

| Resource ID (Antora)
| Механизм адресации файлов в Antora (`family$path`), используется в
`xref:`/`image:` для ссылок между страницами, партиалами, вложениями.

| BPMN
| Business Process Model and Notation — нотация для описания бизнес-процессов
с дорожками (lanes), задачами, шлюзами (gateways) и событиями. Используется
для описания процесса обработки лида, в отличие от диаграмм состояний,
которые описывают только сам ресурс.

| Kroki
| Сервис рендеринга диаграмм из текстового описания (Mermaid, BPMN, PlantUML
и др.) в SVG. В проекте развёрнут локально через Docker Compose, без
обращения к публичному `kroki.io`.

| Test Case
| Тест-кейс — описание проверки: предусловия, шаги и ожидаемый результат.
Идентификаторы вида `TC-<ОБЛАСТЬ>-<номер>` — см.
xref:standarts/test-case-standart.adoc#_идентификаторы_тест_кейсов[стандарт оформления тест-кейсов].

| Bug Report
| Баг-репорт — формализованное описание дефекта: окружение, шаги
воспроизведения, ожидаемый и фактический результат, ссылка на контракт.
Примеры — xref:testing/bug-reports.adoc#BR-001[Баг-репорты].

| Severity
| Серьёзность дефекта — степень влияния на систему (Blocker, Critical, Major,
Minor, Trivial). Определяется тестировщиком.

| Priority
| Приоритет — срочность исправления дефекта (High/Medium/Low и т.п.).
Определяется бизнесом/менеджером и может не совпадать с severity.

| Smoke-тестирование
| Минимальный набор проверок критических сценариев перед релизом — «дымовой
тест». Чек-лист — xref:testing/checklists.adoc#_smoke_чеклист_перед_каждым_релизом[Чек-листы].

| Regression-тестирование
| Повторная проверка существующей функциональности после изменений для
подтверждения отсутствия регрессов. Чек-лист — xref:testing/checklists.adoc#_regression_чеклист[Чек-листы].
|===
