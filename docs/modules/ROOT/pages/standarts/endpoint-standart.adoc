= Стандарт документации эндпоинтов API

Этот документ описывает единый стандарт оформления документации к эндпоинтам REST API
(формат AsciiDoc). Все файлы с описанием ресурсов и операций должны следовать этой структуре.

== Структура файла ресурса

Каждый файл документации включает разделы в следующем порядке:

1. Заголовок уровня 1 (`=`) — название ресурса или раздела API.
2. Вводный абзац — 1–2 предложения, кратко описывающих назначение ресурса/раздела.
3. `== Модель данных` — таблица полей ресурса. Обязательна для ресурсов с CRUD-операциями
   (leads, deals и т.п.). Не требуется для служебных разделов без собственной сущности
   (например, аутентификация).
4. Один раздел `==` на каждый эндпоинт, оформленный по правилам ниже, в порядке
   `GET (список) → POST → GET (по id) → PATCH/PUT → DELETE`.
5. Дополнительные разделы `==` (например, «Использование токена») — при необходимости,
   в конце файла.

== Заголовок эндпоинта

Заголовок — уровень 2 (`==`), метод и путь всегда оформляются как единый inline-код:

----
== `МЕТОД /путь`
----

Примеры: `` == `GET /leads` ``, `` == `POST /auth/token` ``, `` == `PATCH /leads/\{id\}` ``.

Сразу под заголовком — одно предложение, кратко описывающее, что делает эндпоинт
(например: «Возвращает постраничный список лидов.»).

== Таблица модели данных

Колонки: `Поле | Тип | Обязательное | Описание`.
Для полей, генерируемых сервером (`id`, `createdAt`, `updatedAt` и т.п.), в колонке
«Обязательное» ставится «—».

== Подразделы внутри описания эндпоинта

Внутри каждого `==`-раздела эндпоинта используются подразделы `===` в следующем порядке
(включаются только применимые к данному эндпоинту):

[cols="1,3"]
|===
| Подраздел | Когда включается

| `=== Path-параметры`
| Путь содержит `\{id\}` и т.п. Таблица `Параметр \| Тип \| Описание`.

| `=== Query-параметры`
| Эндпоинт принимает параметры фильтрации/пагинации (обычно GET-список). Таблица `Параметр \| Тип \| Описание`.

| `=== Тело запроса`
| POST/PATCH/PUT. JSON-пример (`[source,json]`); таблица полей добавляется, только если тело отличается от модели данных ресурса.

| `=== Пример запроса`
| Всегда. Блок `[source,bash]` с `curl`. Для защищённых эндпоинтов включает заголовок `Authorization: Bearer <token>`.

| `=== Пример ответа \`<код> <статус>\``
| Для эндпоинтов, возвращающих тело (не требуется для `204 No Content`). Блок `[source,json]`.

| `=== Поля ответа`
| Только если структура ответа не покрывается таблицей «Модель данных» ресурса (например, ответ выдачи токена). Таблица `Поле \| Тип \| Описание`.

| `=== Возможные ошибки`
| Всегда, если у эндпоинта есть нетривиальные ошибки (400/401/404/409 и т.п.), включая `404 Not Found` для операций с `\{id\}`. Таблица `Код \| Описание \| Пример` — не абзац текста.
|===

== Общие правила

- Язык документации — русский.
- Имена полей в JSON — camelCase (`fullName`, `clientId`).
- Идентификаторы ресурсов — короткий буквенный префикс + `_` + номер (`ld_1001` для leads);
  для новых ресурсов использовать аналогичную схему.
- Все защищённые эндпоинты в примерах `curl` содержат заголовок
  `Authorization: Bearer <token>`.
- Раздел «Возможные ошибки» всегда оформляется таблицей `Код | Описание | Пример`.
- `DELETE`-эндпоинты обязательно документируют `204 No Content` (успех, без тела) и
  `404 Not Found` (ресурс не найден) в таблице ошибок.
- `GET /resource/\{id\}` обязательно документирует `404 Not Found` в таблице ошибок.
