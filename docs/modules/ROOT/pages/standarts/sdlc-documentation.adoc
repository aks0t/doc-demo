= Жизненный цикл разработки ПО и документация

Этот документ описывает, какие артефакты документации требуются на каждом этапе
жизненного цикла разработки ПО (SDLC), кто их обычно создаёт и какова роль
технического писателя на каждом этапе.

Опирается на процессную модель из ISO/IEC/IEEE 12207 (Software life cycle
processes) и адаптирован под серию стандартов документирования
ISO/IEC/IEEE 26511-26515.

== Зачем это нужно техническому писателю

Типичная ошибка — думать, что документация появляется только после того, как
продукт готов ("напишем доку в конце"). На практике для каждого этапа SDLC
существует свой набор документов, и часть из них создаётся *до* написания кода,
а не после. Технический писатель, который понимает эту последовательность, может:

* включаться в discovery до начала разработки, а не постфактум;
* закладывать в требования критерии тестируемости и документируемости;
* избегать ситуации, когда документация навсегда отстаёт от продукта.

== Этапы, документы и роль писателя

[cols="2,3,4,3"]
|===
| Этап | Что происходит | Ключевые документы | Роль технического писателя

| Инициация / анализ требований
| Формулируется бизнес-задача, собираются требования от стейкхолдеров, оценивается
целесообразность.
| * Business Requirements Document (BRD)
* Vision & Scope Document
* User Stories / UseCase
* Software Requirements Specification (SRS)
| Участвует в discovery: интервью со стейкхолдерами, фиксация требований в
структурированном виде. На этом этапе документация формирует основу для будущего
контента, а не пишется параллельно с ним.

| Проектирование (Design)
| Определяется архитектура решения, интерфейсы, модели данных.
| * High-Level Design (HLD) / Low-Level Design (LLD)
* Architecture Decision Records (ADR)
* API-спецификация (черновик OpenAPI/Swagger)
* ER-диаграммы, Sequence-диаграммы, Deployment-диаграммы
| Документирует архитектурные решения вместе с разработчиками/архитекторами,
готовит черновики API-спек до реализации — это позволяет проверить контракт API
на этапе, когда его ещё дёшево менять.

| Разработка (Development)
| Пишется код, реализуются фичи согласно дизайну.
| * Coding Standards / Style Guide
* Живая API-документация (обновляется по мере разработки)
* Inline-документация / комментарии в коде
* Записи в базе знаний (Confluence/Notion) по нестандартным решениям
| Встраивается в цикл разработки: обновляет документацию синхронно с изменениями
кода (а не по итогам спринта), ведёт стандарт оформления документации команды.

| Тестирование (QA)
| Проверяется соответствие требованиям, находятся и фиксируются дефекты.
| * Test Plan
* Test Cases / Test Scripts
* Отчёты о тестировании (QA Reports)
* Acceptance Criteria / UAT Sign-off
| Документирует известные ограничения и edge-cases, помогает формулировать
критерии приёмки в понятном для бизнеса и тестировщиков виде.

| Развёртывание / релиз (Deployment)
| Продукт выкатывается в продуктивную среду.
| * Release Notes / Changelog
* Deployment Guide / Runbook
* Rollback Plan
* Installation / Migration Guide
| Готовит release notes для разных аудиторий (внутренние команды vs внешние
пользователи), поддерживает runbook в актуальном состоянии.

| Эксплуатация и поддержка (Maintenance)
| Продукт используется, дорабатывается, исправляются баги.
| * User Manual / Guides
* FAQ / База знаний
* Troubleshooting Guide
* SLA / Support Documentation
| Основной объём работы технического писателя приходится именно сюда: ведение и
актуализация базы знаний, реагирование на изменения продукта.

| Вывод из эксплуатации (Retirement / EOL)
| Продукт или его часть выводится из использования.
| * Deprecation Notice
* Migration Guide (переход на замену)
* Архивация документации
| Готовит уведомления об устаревании функциональности заранее, а не постфактум,
и обеспечивает, чтобы архивная документация оставалась доступной, но помеченной
как устаревшая.
|===

== Как это применимо к Agile / итеративной разработке

В классическом waterfall эти этапы идут последовательно один раз. В Agile/Scrum
тот же набор документов существует, но переиспользуется на каждой итерации в
сокращённом виде:

[cols="1,3"]
|===
| Waterfall-документ | Agile-эквивалент

| BRD / SRS
| Epic + User Stories в бэклоге, Definition of Ready

| HLD/LLD
| Технический дизайн-документ на фичу / RFC перед крупными изменениями

| Test Plan
| Acceptance Criteria внутри User Story, чек-лист DoD (Definition of Done)

| Release Notes
| Changelog на каждый релиз/спринт, а не на весь продукт разом
|===
