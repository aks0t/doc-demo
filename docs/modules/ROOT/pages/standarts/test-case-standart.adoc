= Стандарт оформления тест-кейсов

Этот документ описывает единый стандарт оформления тестовой документации
(формат AsciiDoc) в разделе «Тестирование». Все файлы тест-кейсов,
баг-репортов и чек-листов должны следовать этой структуре.

Стандарт дополняет xref:standarts/endpoint-standart.adoc[Стандарт документации эндпоинтов API]:
тест-кейсы описывают ожидаемое поведение интерфейса, которое обязано
соответствовать контракту `openapi/openapi.yaml`.

== Идентификаторы тест-кейсов

Схема ID: `TC-<ОБЛАСТЬ>-<номер>`.

[cols="1,1,3"]
|===
| Область | Префикс | Пример

| Аутентификация | `AUTH` | `TC-AUTH-01`

| Список лидов | `LIST` | `TC-LIST-04`

| Форма лида | `FORM` | `TC-FORM-07`

| Смена статуса | `STATUS` | `TC-STATUS-05`
|===

Нумерация сквозная и не меняется при удалении кейсов — номера удалённых кейсов
не переиспользуются (это сохраняет ссылки в отчётах и историю).

== Таблица тест-кейса

Обязательные колонки:

[cols="1,3"]
|===
| Колонка | Описание

| `ID`
| Уникальный идентификатор по схеме `TC-<ОБЛАСТЬ>-<NN>`.

| `Предусловия`
| Состояние системы и данные, необходимые для выполнения шагов.

| `Шаги`
| Нумерованный список действий. Многострочные шаги разделяются `+` в конце строки.

| `Ожидаемый результат`
| Что должно произойти после выполнения шагов. Для негативных кейсов —
  включая конкретный код ошибки API (`409 duplicate_email` и т.п.), а не
  абстрактное «ошибка».

| `Приоритет`
| High / Medium / Low.

| `Тип`
| Позитивный / Негативный / Граничный / UI / Адаптив.
|===

Пример:

[source,adoc]
----
[cols="1,3,3,3,1,1"]
|===
| ID | Предусловия | Шаги | Ожидаемый результат | Приоритет | Тип

| TC-FORM-07
| В системе уже есть лид с email ivan.petrov@example.com; открыта форма создания лида
| 1. Заполнить email = ivan.petrov@example.com +
2. Заполнить остальные поля корректно +
3. Нажать «Сохранить»
| Под полем email отображается «Лид с таким email уже существует»; POST /leads вернул `409 duplicate_email`
| High
| Негативный
|===
----

== Связь с контрактом API

Каждый негативный тест-кейс должен проверять, что интерфейс обрабатывает
**именно тот код ошибки**, который задокументирован в контракте:

* код ошибки — из перечисления `Error.code` в `openapi/openapi.yaml`
  (xref:api/errors.adoc[Ошибки и коды состояния]);
* HTTP-статус — из `responses` соответствующей операции.

Если поведение UI зависит от конкретной ошибки, в «Ожидаемый результат»
обязательно указывается этот код.

== Баг-репорты

Поля баг-репорта:

* `ID` — схема `BR-<номер>`;
* `Заголовок`;
* `Окружение` — браузер, версия, ОС, окружение (staging/prod);
* `Приоритет / Severity` — два значения через слэш;
* `Предусловия`;
* `Шаги воспроизведения`;
* `Ожидаемый результат`;
* `Фактический результат`;
* `Ссылка на контракт` — xref:api/errors.adoc[] и/или xref:api/endpoints/leads.adoc[];
* `Скриншот`;
* `Статус`.

Разница Severity и Priority объяснена на странице
xref:testing/bug-reports.adoc[Баг-репорты].

== Чек-листы

Формат — маркированный список с флажками `- [ ]`. Каждый пункт — одна
проверяемая сущность. Группировка по фичам/областям обязательна.
