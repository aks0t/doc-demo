= REST, SOAP, GraphQL: разница в подходе к документированию

Весь этот проект документирует REST API. Ниже — не практический пример (его здесь
нет), а сжатый разбор того, чем отличается подход к документированию, если протокол
другой. Полезно держать в голове, что "документирование API" — не синоним
"документирования REST".

[cols="1,3,3,3"]
|===
| | REST | SOAP | GraphQL

| Контракт
| OpenAPI/Swagger (YAML/JSON), декларативный, отделён от кода
| WSDL (XML) — жёстко типизированный контракт, часто генерируется из кода
(contract-last) или задаёт код (contract-first)
| Схема (SDL — Schema Definition Language): типы, запросы, мутации, подписки

| Единица документирования
| Ресурс + HTTP-метод (`GET /leads`, `POST /leads`)
| Операция (`CreateLead`, `GetLeadById`) — привязки к HTTP-методам нет,
всё обычно идёт через `POST`
| Тип и поле схемы, а не эндпоинт — эндпоинт как правило один (`/graphql`)

| Как показываются ошибки
| HTTP-коды состояния (`400`, `404`, `409`) + тело ответа
| SOAP Fault — отдельная XML-структура внутри тела ответа, HTTP-код почти
всегда `200` независимо от бизнес-результата
| HTTP `200` почти всегда, ошибки — в поле `errors` тела ответа, отдельно от `data`

| Инструмент документирования
| Swagger UI / Redoc, генерируется из спеки
| WSDL сам по себе слабо читаем человеком — обычно документируется вручную
(таблицы операций, примеры XML-конвертов)
| GraphiQL / GraphQL Playground — интроспекция схемы встроена в протокол,
документация по типам генерируется автоматически

| Версионирование
| В пути (`/v1/`) или в заголовке
| В `targetNamespace` WSDL или отдельным неймспейсом операций
| Обычно не версионируется явно — поля помечаются `@deprecated`,
схема эволюционирует аддитивно
|===

== Что из этого переносится в практику независимо от протокола

* Единый источник правды (спека/схема/WSDL), из которого генерируется читаемая
документация, а не наоборот.
* Живые, проверяемые примеры запросов — расхождение между примером и реальным
поведением API одинаково больно ломает доверие к документации что в REST,
что в SOAP, что в GraphQL.
* Явное описание кодов/типов ошибок — в GraphQL и SOAP это менее очевидно
для читателя, чем HTTP-код, а значит требует более явного объяснения в тексте,
а не только в схеме.
