= Чек-листы

Четыре практических чек-листа: smoke перед релизом, regression по фичам,
кросс-браузерный/адаптивный и accessibility. Используются при ручном прогоне.

== Smoke-чеклист (перед каждым релизом)

Минимальный набор, который выполняется за 15–20 минут:

- [ ] Авторизация: вход с валидными учётными данными проходит
- [ ] Авторизация: неверный пароль показывает понятную ошибку
- [ ] Список лидов: открывается, данные отображаются
- [ ] Создание лида: happy path (создаётся лид со статусом `new`)
- [ ] Смена статуса: `new → in_progress` проходит
- [ ] Список лидов обновляется после создания лида (без перезагрузки страницы)

== Regression-чеклист

Сгруппирован по фичам. Выполняется перед выкатом изменений в общие области.

=== Auth

- [ ] Вход с корректными учётными данными
- [ ] Вход с неверным `clientSecret`
- [ ] Пустые обязательные поля формы логина подсвечены
- [ ] Истёкший токен: пользователь перенаправлен на логин

=== Leads list

- [ ] Фильтр по каждому статусу (`new`, `in_progress`, `qualified`, `closed`)
- [ ] Пагинация: переходы вперёд/назад, отображение активной страницы
- [ ] Пустое состояние при отсутствии лидов
- [ ] Список не ломается при длинных значениях `fullName`

=== Lead form

- [ ] Создание лида с корректными данными
- [ ] Редактирование полей `fullName`/`phone`/`email`/`source`
- [ ] Валидация `email` (обязательность, формат)
- [ ] Валидация `phone` (формат E.164)
- [ ] Дубль email → ошибка `duplicate_email` у поля
- [ ] Недопустимый `source` → ошибка валидации
- [ ] Кнопка «Сохранить» disabled при невалидной форме

=== Status change

- [ ] Переход `new → in_progress`
- [ ] Переход `in_progress → qualified`
- [ ] Переход `in_progress → closed`
- [ ] Переход `qualified → closed`
- [ ] Недопустимый переход (`new → qualified`) показывает ошибку у поля

== Cross-browser / адаптив чеклист

Проверяется на:

* Chrome (desktop) + Firefox (desktop) + Safari (desktop);
* 1 мобильный viewport (375px) в Chrome DevTools.

На что смотреть:

- [ ] Текст не обрезается и не наезжает на соседние элементы
- [ ] Кнопки не переносятся и не слипаются (кнопка «Сохранить», пагинация)
- [ ] Модальные окна не перекрывают контент (z-index корректен)
- [ ] Таблица лидов на мобильном viewport: горизонтальный скролл или карточный вид, без обрезания колонок
- [ ] Ошибки валидации отображаются под полями и не перекрываются
- [ ] Шрифты не «пляшут» между браузерами (один и тот же рендер заголовков)
- [ ] Нет горизонтального скролла всей страницы (кроме случаев, когда это заложено)

== Accessibility (a11y) чек-лист

Базовые проверки доступности. Выполняются в Chrome + Lighthouse (пункты, помеченные «скринридер», — вручную с NVDA/VoiceOver или через проверку в DevTools):

- [ ] У каждого поля формы есть видимый `<label>`, связанный с полем (`for`/`id`)
- [ ] Ошибки валидации привязаны к полю (`aria-describedby`) и объявляются как `role="alert"` / `aria-live`
- [ ] Фокус после отправки формы с ошибками переходит на первое невалидное поле
- [ ] Все интерактивные элементы (кнопки, ссылки, поля) доступны с клавиатуры (Tab/Shift+Tab)
- [ ] Видимый focus-индикатор присутствует на всех интерактивных элементах
- [ ] Контраст текста соответствует WCAG AA (4.5:1 для обычного текста)
- [ ] Таблица списка лидов читается скринридером: корректные `<th>` и роль таблицы
- [ ] Иконки и кнопки без текста имеют `aria-label` или видимый текст
- [ ] Модальные окна и уведомления не «съедают» фокус и возвращают его после закрытия
- [ ] Lighthouse (Accessibility) — нет ошибок красного уровня, минимум жёлтых
