= Баг-репорты (примеры)

Ниже приведены примеры оформления баг-репортов. Первые два — гипотетические
дефекты Admin UI, вытекающие из проверки соответствия интерфейса контракту API.
Они демонстрируют, как UI обязан отображать ошибки, задокументированные в
`openapi/openapi.yaml`.

== Severity vs Priority

* **Severity (серьёзность)** — насколько сильно дефект влияет на систему:
  * Blocker — система не работает вообще;
  * Critical — критическая функция не работает, нет обходного пути;
  * Major — функция работает, но с существенными ограничениями;
  * Minor — незначительное отклонение;
  * Trivial — косметика.
* **Priority (приоритет)** — насколько срочно нужно исправить. Определяется
  бизнесом/менеджером и не всегда совпадает с severity. Например, дефект
  severity Major может получить низкий приоритет, если затрагивает только
  редкий сценарий.

== BR-001: Ошибка 409 duplicate_email отображается как «Something went wrong»

[cols="1,3"]
|===
| Поле | Значение

| ID | BR-001
| Заголовок | Ошибка 409 duplicate_email отображается как «Something went wrong»
| Окружение | Chrome 126, Windows 11 / Admin UI (staging)
| Приоритет / Severity | Priority: Medium, Severity: Major
| Предусловия | В системе уже есть лид с email ivan.petrov@example.com
| Шаги воспроизведения | 1. Открыть форму создания лида +
2. Указать email ivan.petrov@example.com +
3. Заполнить остальные поля корректно +
4. Нажать «Сохранить»
| Ожидаемый результат | Под полем email: «Лид с таким email уже существует»
| Фактический результат | Показывается баннер «Something went wrong», без указания поля
| Ссылка на контракт | xref:api/errors.adoc#_коды_ошибок_бизнес_логики[] — код `duplicate_email`; `POST /leads` → `409` в xref:api/endpoints/leads.adoc#_post_leads[]
| Скриншот | (приложить)
| Статус | Open
|===
