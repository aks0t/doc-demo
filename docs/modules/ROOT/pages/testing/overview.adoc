= Обзор: подход к тестированию

Этот раздел описывает, как тестируется условный веб-интерфейс (Admin UI) поверх
CRM Leads API. Здесь собраны тест-кейсы, чек-листы, примеры баг-репортов и
итоговый отчёт по прогону.

== Объект тестирования

Условный веб-интерфейс (Admin UI) поверх CRM Leads API — экраны:

* форма логина;
* список лидов (с фильтром по статусу и пагинацией);
* карточка лида (создание, редактирование, смена статуса).

[IMPORTANT]
====
UI как отдельный код в этом репозитории не реализован; тест-кейсы описывают
ожидаемое поведение интерфейса, полностью соответствующее контракту
`openapi/openapi.yaml`. Такой подход применяется, когда интерфейс находится в
разработке: тестовая документация пишется как спецификация ожидаемого поведения,
а не как описание уже существующего экрана.
====

== Уровни тестирования

[cols="1,3"]
|===
| Уровень | Что покрывается

| Функциональное (UI)
| Поведение экранов: валидация форм, отображение ошибок, переходы статусов,
состояния кнопок и полей. Основа — тест-кейсы в xref:testing/test-cases/auth.adoc#_таблица_кейсов[Логин],
xref:testing/test-cases/leads-list.adoc#_таблица_кейсов[Список лидов],
xref:testing/test-cases/lead-form.adoc#_таблица_кейсов[Форма лида],
xref:testing/test-cases/lead-status.adoc#_таблица_кейсов[Смена статуса].

| API-smoke (Postman)
| Ключевые сценарии на уровне контракта: получение токена, создание лида,
дубликат email, несуществующий id, недопустимый переход статуса.
Коллекция — `qa/api-tests/crm-leads-smoke.postman_collection.json`.

| Нефункциональное (по минимуму)
| Кросс-браузерность и адаптивность — чек-лист в
xref:testing/checklists.adoc#_cross_browser_адаптив_чеклист[Чек-листы].
|===

== Инструменты

* Браузер + DevTools — ручная проверка UI, анализ структуры DOM, состояний
  элементов и сообщений об ошибках.
* Postman — API-smoke-тесты по коллекции
  `qa/api-tests/crm-leads-smoke.postman_collection.json`.
* Таск-трекер — учёт багов (в этом репозитории условно; примеры оформления —
  xref:testing/bug-reports.adoc#BR-001[Баг-репорты]).

== Матрица трассируемости

Каждый тест-кейс можно проследить до функции API и обратно: экран UI должен
отражать поведение, задокументированное в контракте.

[cols="1,1,1"]
|===
| Функция API | Экран UI | Тест-кейсы

| `POST /auth/token`
| Форма логина
| TC-AUTH-01…05

| `GET /leads`, query `status`/`page`/`pageSize`
| Список лидов (фильтр, пагинация)
| TC-LIST-01…08

| `POST /leads`
| Форма создания лида
| TC-FORM-01…10

| `PATCH /leads/{id}` (статус)
| Смена статуса в карточке
| TC-STATUS-01…06
|===

Такой же подход к связыванию сущностей уже используется в
xref:api/data-model.adoc#_текущая_модель[модели данных API] — тестовая
документация строится по тем же принципам.
