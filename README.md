# Демо-документация CRM Leads API

Портфолио-проект на позицию технического писателя, построенный по принципу
**Docs-as-Code**: контент хранится в Git рядом с OpenAPI-спекой, собирается
генератором **Antora**, диаграммы рендерятся локальным Kroki без обращения к
внешним сервисам, публикация выполняется автоматически через GitHub Actions на
GitHub Pages.

API — вымышленный (CRM Leads API). Документация и инфраструктура вокруг неё —
рабочие: включая те проблемы, с которыми пришлось разбираться по ходу (о них —
ниже), и то, как они были решены.

**Сайт:** https://aks0t.github.io/doc-demo

## Требования

* Node.js 18+
* Docker + Docker Compose — необходимы для локального рендера диаграмм.
  Без них `build.sh` завершится с понятной ошибкой, а не тихо пропустит шаг.

## Как собрать локально

```bash
./build.sh
```

Скрипт выполняет всё последовательно:

1. поднимает через `docker compose` три контейнера — `kroki`, `kroki-mermaid`,
   `kroki-bpmn` (см. `docker-compose.yml`) — и дожидается готовности Kroki;
2. устанавливает npm-зависимости, если их ещё нет;
3. собирает сайт в `build/site`;
4. запускает live-server на `http://localhost:8080` с live-reload при
   изменении `.adoc`-файлов.

Вручную, без live-server:

```bash
docker compose up -d
npm install
npx antora antora-playbook.yml
```

## Диаграммы: почему используется Docker Compose, а не один контейнер

Основной образ `yuzutech/kroki` поддерживает PlantUML и GraphViz из коробки.
Mermaid и BPMN рендерятся отдельными контейнерами-компаньонами
(`yuzutech/kroki-mermaid`, `yuzutech/kroki-bpmn`), к которым Kroki обращается
по сети. Без них сборка не падает — диаграмма просто не рендерится, а в логе
остаётся `WARN ... Skipping mermaid block`. Поэтому в репозитории —
`docker-compose.yml`, поднимающий все три контейнера одновременно.

Kroki-сервер используется **локальный**, а не публичный `kroki.io`: сборка,
завязанная на внешний сервис, время от времени падает или рендерит не все
диаграммы из-за сетевых таймаутов и rate-limit. Локальный сервер применяется
и в `build.sh`, и в CI (см. `services:` в
`.github/workflows/publish-docs.yml` — те же три контейнера как
сервис-контейнеры на `localhost:8000`), поэтому сборка не зависит от внешней
сети.

Версия `asciidoctor-kroki` закреплена на ветке `0.18.x` (`asciidoctor-kroki@latest-0`
в терминах npm-тегов). Версия 1.x требует Asciidoctor.js 4.0, который Antora
3.x пока не поддерживает; попытка использовать 1.x приводит к ошибке сборки
`block.$!= is not a function` — следствие двух несовместимых копий
Asciidoctor.js в дереве зависимостей.

Если диаграммы не рендерятся локально:

1. `docker info` — проверить, что Docker-демон запущен.
2. `docker compose ps` — проверить, что все три контейнера подняты.
3. `curl http://localhost:8000` — проверить, что Kroki отвечает.
4. `docker compose logs kroki` / `logs mermaid` / `logs bpmn` — посмотреть логи.
5. В выводе `antora --stacktrace` найти строки `WARN (asciidoctor)` — там
   указана точная причина.

## Спецификация (Redoc)

OpenAPI-спека рендерится через Redoc, встроенный через `<iframe>`, а не через
CDN-скрипт, инициализируемый прямо внутри узкой колонки контента Antora. Redoc
рассчитан на полноэкранный layout, и его внутренняя адаптивность работает
корректно только в изолированном документе — отсюда и `iframe`.

## Почему Antora, а не Confluence

Осознанный выбор инструмента, а не ограничение. Confluence хорошо подходит для
внутренней базы знаний, но менее удобен для документации API, которая должна
жить в репозитории рядом с кодом, проходить код-ревью и собираться в
статический сайт.

| Концепт в проекте | Аналог в Confluence |
|---|---|
| `.adoc`-файлы в `docs/modules/ROOT/pages/` | Страницы в пространстве |
| `nav.adoc` | Дерево страниц в sidebar |
| OpenAPI-спека | Swagger-макрос или ручное описание |
| Стандарт оформления эндпоинтов | Шаблон страницы |
| Переиспользуемые блоки (partials) | Excerpts |
| Antora + GitHub Actions | Плагин публикации / Scroll |
| Диаграммы через Kroki | Gliffy / Draw.io |

Всё, что реализовано здесь в Antora, воспроизводимо и в Confluence — но с
большими затратами на ручное поддержание консистентности. В реальной компании
разумен гибрид: внешняя (или партнёрская) документация — статический сайт из
Git, внутренняя база знаний — Confluence, но единый источник правды для
API-описаний — Git и OpenAPI.

## Состав документации

* OpenAPI-спека синхронизирована с текстовой документацией: единый формат
  ошибок, общая схема `ErrorResponse`, теги, примеры на каждый код ответа.
* Диаграммы: sequence (аутентификация), state (статусы лида), BPMN
  (бизнес-процесс обработки лида с тремя дорожками — маркетинг, продажи,
  CRM), deployment (пайплайн сборки документации). Все диаграммы кликабельны
  и открываются в лайтбоксе с зумом и панорамированием.
* Единый стандарт оформления эндпоинтов (`standarts/endpoint-standart.adoc`)
* Шаблон discovery-отчёта и страница о необходимых документах на каждом этапе
  SDLC.
* Глоссарий терминов (`glossary.adoc`).
* `CHANGELOG.md` — история изменений документации и продукта.

## Публикация (CI/CD)

При пуше в `main` GitHub Actions выполняет:

1. установку зависимостей (`npm ci`);
2. запуск Kroki и контейнеров-компаньонов как сервис-контейнеров с ожиданием
   готовности;
3. сборку статического сайта;
4. публикацию на GitHub Pages.

См. [`.github/workflows/publish-docs.yml`](.github/workflows/publish-docs.yml).
